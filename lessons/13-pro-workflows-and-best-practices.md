Quick reminders of words you already know, used throughout:

- **Repository (repo)** = your project folder plus Git's hidden history
  database (the `.git/` folder).
- **Commit** = a saved snapshot of your whole project, with a message.
- **Tracked file** = a file Git is already watching (it is in at least one
  commit or in the staging area).
- **Untracked file** = a file in your folder that Git has not been told to
  watch yet.
- **Remote** = a copy of the repo on another machine, usually GitHub.

## `.gitignore` — Keeping Junk Out of Your Repo

### Why do we need this?

Analogy: when you zip a project to send to a colleague, you would not
include your `venv/` folder, your `__pycache__/`, or a file with your
passwords. You pick what goes in the box.

Git has the same problem. By default, `git status` lists every new file
in your folder, and `git add .` would happily save all of them forever.
Some of those files are:

- Noise (compiled files, logs, editor settings).
- Huge and re-creatable (dependency folders like `.venv/`).
- Dangerous (passwords, API keys, private certificates).

**`.gitignore`** is a plain text file in your repo. Each line is a
pattern. Git pretends any file matching a pattern does not exist.

Python analogy: it works like the `exclude` list you might pass to a
file-collection function, or `--ignore` in a `pytest` run. It filters
what gets picked up.

### See the problem first

Imagine a Python test project with a virtual environment and a secrets
file:

```bash
git status
```

Expected output (before any `.gitignore`):

```
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.env
	.venv/
	__pycache__/
	tests/

nothing added to commit but untracked files present (use "git add" to track)
```

Line by line:

- `Untracked files:` — these are files Git sees but is not watching.
- `.env` — holds secrets. We must never commit this.
- `.venv/` and `__pycache__/` — generated by Python. Useless to others.
- `tests/` — real work we do want.

Risk: one careless `git add .` and the secret is in history.

### The fix

Create a file named exactly `.gitignore` at the top of the repo:

```gitignore
# Python
__pycache__/
*.pyc
.venv/
venv/
*.egg-info/

# Environment / secrets — NEVER commit these
.env
.env.local
*.pem
*.key

# Editor/OS
.DS_Store
.vscode/
.idea/

# Build output
dist/
build/
*.log
```

Run status again:

```bash
git status
```

Expected output:

```
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	tests/

nothing added to commit but untracked files present (use "git add" to track)
```

What changed: `.env`, `.venv/`, and `__pycache__/` vanished from the
list. Git now ignores them. `.gitignore` itself appears, because you
should commit it so your teammates get the same rules.

### Pattern rules, one at a time

| Pattern | Meaning | Example match |
|---|---|---|
| `.env` | A file with this exact name, anywhere in the repo | `.env`, `config/.env` |
| `*.log` | `*` means "any characters". Any file ending in `.log` | `app.log`, `logs/run.log` |
| `build/` | A trailing `/` means "this is a folder" | the `build` folder and everything in it |
| `# text` | A line starting with `#` is a comment | (ignored by Git) |
| `!keep.log` | `!` means "un-ignore": an exception to an earlier rule | keeps `keep.log` even though `*.log` is ignored |

Example of an exception:

```gitignore
*.log
!important.log
```

Meaning: ignore all `.log` files, except `important.log`.

Rule of thumb: one pattern per line, and order matters. A later line can
override an earlier one.

### Check why a file is ignored

If you are unsure whether a rule works, ask Git:

```bash
git check-ignore -v .env
```

Expected output:

```
.gitignore:8:.env	.env
```

Reading it: "the file `.env` is ignored because of line 8 of
`.gitignore`, which contains the pattern `.env`". If the command prints
nothing, the file is not ignored.

### Common confusion: "I added it to `.gitignore` but Git still tracks it!"

This is the number one `.gitignore` doubt. The answer:

**`.gitignore` only affects untracked files.** If a file was already
committed, Git is already watching it. Adding a rule later does nothing
to a file Git already knows.

Analogy: putting a "do not deliver" sign on your door does not recall the
parcels already delivered.

How to read this: ask the questions top to bottom for any file. Each
answer sends you down one labelled path.

```
  Is the file already TRACKED (in a commit or staged)?
        |
       yes                                  no (untracked)
        |                                     |
        v                                     v
  .gitignore has NO effect.         Does a .gitignore pattern match?
  Git keeps watching it.                  |            |
  Fix: git rm --cached <file>            yes           no
       then commit                        |            |
                                          v            v
                                    IGNORED:       UNTRACKED:
                                    hidden from    listed by git status;
                                    status/add     git add can save it
```

What changed: nothing yet; this shows why a late `.gitignore` rule
cannot un-track a file. Only `git rm --cached` moves it from the left
path to the right.

The fix is to tell Git to stop watching the file, without deleting it from
your disk:

```bash
git rm --cached .env
```

Expected output:

```
rm '.env'
```

Meaning:

- `git rm` normally removes a file from Git AND from disk.
- `--cached` means "only remove it from Git's tracking (the staging
  area), leave the real file on disk".

Then check:

```bash
git status
```

```
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    .env
```

Read "deleted: .env" carefully: it means "deleted from Git's tracking
in the next commit". Your real `.env` file is still sitting in your
folder. Now commit:

```bash
git commit -m "Stop tracking .env"
```

Important: the old copies of `.env` still exist in earlier commits. This
only stops *future* tracking. If `.env` had secrets, read the next
section.

### Templates and global ignores

- Do not write a `.gitignore` from scratch for a common language. GitHub
  keeps good starter templates per language at
  https://github.com/github/gitignore. Copy the `Python.gitignore` one.
- Some clutter belongs to *you*, not the project (for example `.DS_Store`,
  which macOS creates). Put those in a **global ignore file** that applies
  to every repo on your machine:

```bash
echo ".DS_Store" >> ~/.gitignore_global
git config --global core.excludesfile ~/.gitignore_global
```

The first line appends `.DS_Store` to a file in your home folder. The
second tells Git "also read this file for ignore rules in every repo".
Neither command prints anything on success.

### If You Already Committed a Secret

Why this is serious: in Lesson 03 you learned that Git stores every
version of every file as an object, and old commits are kept. So a
password that was committed once is in history even after you delete the
file in a later commit. Anyone who can clone the repo can dig it out.

Analogy: tearing a page out of today's notebook does not remove the
photocopy someone already made.

There are two separate jobs. Do both.

**Job 1 (most urgent): revoke the secret.** Go to the service that issued
it (AWS, GitHub, a database, etc.) and rotate or revoke the credential, so
the leaked one stops working. Treat any leaked secret as stolen, even if
you clean history afterwards. Why: someone may already have cloned it,
and bots scan public GitHub for keys within minutes.

**Job 2: remove it from history.** Deleting it in a new commit is not
enough. You must rewrite history so no commit contains it.
`git filter-repo` is the modern recommended tool (it replaces the older
`filter-branch`).

```bash
# install first: brew install git-filter-repo
git filter-repo --path secrets.env --invert-paths
```

What the flags mean:

- `--path secrets.env` — "look at this file".
- `--invert-paths` — "remove it (keep everything EXCEPT this path)".

Expected output (abbreviated):

```
Parsed 42 commits
New history written in 0.11 seconds; now repacking/cleaning...
Completely finished after 0.35 seconds.
```

Meaning: Git rewrote all 42 commits so none contain `secrets.env`. Since
every commit's content changed, every commit gets a new hash.

How to read this: a prime (') marks a rewritten commit. Same message and
author, but different content, so a different hash. Say `secrets.env` was
first added in commit B.

BEFORE (command not yet run; hashes are examples):

```
  A---B---C---D          main    (local)
      ^
      secrets.env added here

  hashes: A=a1f  B=9c2  C=4e7  D=b50
```

Command: `git filter-repo --path secrets.env --invert-paths`

AFTER:

```
  A---B'--C'--D'         main    (local, rewritten)

  hashes: A=a1f  B'=7d1  C'=2a9  D'=e03   (B', C', D' are NEW)

  origin/main still points at old D (b50) until you force-push
```

What changed: A is untouched (it never had the file). B, C, D became
B', C', D' with new hashes, and none contain `secrets.env`. The remote
still has the old history until the force push below.

Note: `git filter-repo` also removes your `origin` remote as a safety
measure. You re-add it, then push:

```bash
git remote add origin git@github.com:you/repo.git
git push --force --all
```

`--force` overwrites the remote history. This is dangerous for
teammates, because their copies no longer match. Tell your team first,
and have everyone re-clone afterwards.

## Git Config Worth Setting Up Once

### Why do we need this?

Git has settings (called **config**) for your name, your editor, your
shortcuts, and behavior. Setting them once saves time every day, and some
settings prevent confusing errors.

Analogy: this is like configuring your editor's preferences or your
`pytest.ini`. You do it once; it applies from then on.

### Three levels of config (and who wins)

| Level | Flag | Stored in | Applies to |
|---|---|---|---|
| System | `--system` | machine-wide file | every user on the machine |
| Global | `--global` | `~/.gitconfig` | every repo for your user |
| Local | (no flag) | `.git/config` in the repo | only that repo |

The more specific level wins: local beats global beats system. Python
analogy: like variable scope. The inner (local) value shadows the outer.

### The settings

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"
git config --global pull.rebase false
git config --global fetch.prune true
git config --global color.ui auto
```

None of these print anything when they succeed. Here is what each does:

- `user.name` / `user.email` — stamped on every commit you make.
- `init.defaultBranch main` — new repos start with a branch called `main`
  (newer Git does this already, but being explicit avoids surprises).
- `core.editor "code --wait"` — when Git needs you to type a message
  (commits, rebases), open VS Code. `--wait` makes Git pause until you
  close that file tab; without it Git would think you finished instantly.
- `pull.rebase false` — when you `git pull` and histories have diverged,
  combine them with a merge. Set it to `true` to use a rebase instead.
  The point of writing it down is that Git otherwise prints a warning
  asking you to choose.
- `fetch.prune true` — when a branch is deleted on GitHub, your next
  fetch also removes your stale local reference to it (the
  `origin/feature-x` label), so `git branch -r` doesn't fill up with ghosts.
- `color.ui auto` — colored output in the terminal. Usually already on.

See what you set:

```bash
git config --global --list
```

Expected output:

```
user.name=Your Name
user.email=you@example.com
init.defaultbranch=main
core.editor=code --wait
pull.rebase=false
fetch.prune=true
color.ui=auto
```

Each line is `setting=value`. Notice Git lowercases the key names when
listing; that is normal.

### Aliases — your own shortcuts

An **alias** is a custom short name for a longer command. Python
analogy: `from datetime import datetime as dt`.

```bash
git config --global alias.st status
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.lg "log --oneline --graph --all --decorate"
git config --global alias.last "log -1 HEAD"
```

Now `git st` means `git status`. Try the most useful one:

```bash
git lg
```

Expected output:

```
* a1b2c3d (HEAD -> main, origin/main) Add retry helper
* 9f8e7d6 Fix flaky login test
* 4c3b2a1 Initial commit
```

Reading it: each `*` is a commit; the left is its short hash, then
labels in parentheses (which branches point here), then the message. In
Lesson 05 you typed that whole long command; now it is `git lg`.

`git last` shows only the most recent commit (`log -1 HEAD` = "log, limit
of 1, starting from where HEAD is").

### Per-repo overrides

Common need: you use your personal email for hobby projects but your
company email at work. Do not pass `--global`, so the setting is saved
only in that repo:

```bash
cd work-project
git config user.email "you@company.com"
```

Verify what Git will actually use in this repo:

```bash
git config user.email
```

```
you@company.com
```

Doubt? "How do I know which level a value came from?" Run
`git config --show-origin user.email`. It prints the file it was read
from, for example `file:.git/config	you@company.com`.

## Git Hooks — Automating Checks Locally

### Why do we need this?

You know you should run tests and the linter before committing. You will
forget, on a tired Friday. A **hook** makes the computer remember for you.

Definition: a hook is a script that Git runs automatically at a specific
moment (before a commit, before a push, and so on). If the script exits
with a failure code, Git cancels the action.

Python/test analogy: a hook is like a pytest fixture or `setUp` that is
attached to Git events, except that it can veto the action.

What "exit with a failure code" means: every program ends with a number.
`0` means success, anything else means failure. Git only continues when
the hook returns `0`.

How to read this: follow the arrows down. The hook is a gate in the
middle of the commit; the exit code decides which door opens.

```
  git commit -m "Change login"
            |
            v
  [1] Git runs .git/hooks/pre-commit
            |
            v
  [2] hook script runs (pytest, flake8, ...) and ends with an exit code
            |
       exit code 0 ?
        |             |
       yes            no
        |             |
        v             v
  [3a] commit     [3b] commit BLOCKED
       CREATED         no new commit; your changes stay staged

  History after a PASS:     A---B---C---D*     main
  History after a FAIL:     A---B---C          main  (unchanged)
```

What changed: only on a pass does a new commit D* appear. On a fail,
history is untouched and you fix the problem and commit again.

### Where hooks live

Inside your repo, in the hidden folder `.git/hooks/`.

```bash
ls .git/hooks
```

Expected output:

```
applypatch-msg.sample   pre-commit.sample   pre-push.sample
commit-msg.sample       pre-rebase.sample   update.sample
```

These `.sample` files are examples that do nothing. A hook becomes active
when a file has the exact hook name (no `.sample`) AND is executable.

### Your first hook

Create `.git/hooks/pre-commit`. The very first line must be the
"shebang", which tells the system which program runs the file:

```sh
#!/bin/sh
pytest -q || { echo "Tests failed — commit blocked."; exit 1; }
```

Line by line:

- `#!/bin/sh` — run this file with the shell.
- `pytest -q` — run your tests quietly.
- `||` — "if the thing on the left failed, do the thing on the right".
- `echo ...; exit 1` — print a message, then exit with failure code 1,
  which makes Git cancel the commit.

Make it executable (without this, Git silently ignores it):

```bash
chmod +x .git/hooks/pre-commit
```

Now try to commit while a test fails:

```bash
git commit -m "Change login"
```

Expected output:

```
F                                                              [100%]
FAILED tests/test_login.py::test_valid_user - assert False
1 failed in 0.12s
Tests failed — commit blocked.
```

Then `git log --oneline` shows no new commit. Your changes are still
staged. Fix the test and commit again.

Emergency escape hatch, use rarely:

```bash
git commit --no-verify -m "WIP"
```

`--no-verify` skips the `pre-commit` and `commit-msg` hooks for this one
commit.

### Common hook points

| Hook | Runs | Good for |
|---|---|---|
| `pre-commit` | before the commit is created | lint, format, fast tests |
| `commit-msg` | after you write the message | enforcing message format |
| `pre-push` | before pushing to the remote | slower tests, final gate |

### Common confusion: "Why don't my teammates get my hook?"

Because `.git/` is never part of the commits. Git does not share anything
inside it. Hooks you write by hand live only on your machine. This is by
design: otherwise cloning a repo could run arbitrary scripts on your
computer.

The solution for teams: a tool that keeps the hook *configuration* in a
normal committed file, and installs the hook locally for each person.
Popular ones are [pre-commit](https://pre-commit.com/) (Python-based)
and [Husky](https://typicode.github.io/husky/) (JavaScript-based).

### The `pre-commit` framework

You list the checks in a committed file named `.pre-commit-config.yaml`:

```yaml
repos:
  - repo: https://github.com/psf/black
    rev: 24.4.2
    hooks:
      - id: black
  - repo: https://github.com/pycqa/flake8
    rev: 7.0.0
    hooks:
      - id: flake8
```

What it means:

- `repo` — where the check tool comes from.
- `rev` — the exact version (pinned so everyone runs the same one).
- `id` — which hook from that repo to use (`black` formats code, `flake8`
  finds style errors).

Install and activate it (each teammate runs this once after cloning):

```bash
pip install pre-commit
pre-commit install
```

Expected output of the second command:

```
pre-commit installed at .git/hooks/pre-commit
```

Meaning: the framework wrote a `pre-commit` hook file for you. From now on
each commit runs your listed checks:

```
black....................................................................Passed
flake8...................................................................Failed
- hook id: flake8
- exit code: 1

tests/test_login.py:3:1: F401 'os' imported but unused
```

Reading it: `Passed`/`Failed` per tool. Here flake8 found an unused
import, so the commit is blocked until you fix it. (black often reformats
files itself and reports `Failed`; just `git add` the changes and commit
again.)

## Handling Large Files: Git LFS

(This comes before `.gitattributes` because LFS writes to that file.)

### Why do we need this?

Git stores every version of every file (Lesson 03). For text, Git
compresses changes well. For big binaries like videos, datasets, or
machine-learning model weights, each new version is basically a brand new
huge copy. Change a 500 MB file 10 times and the repo holds about 5 GB,
and every clone downloads all of it. There is no undo for this bloat
short of rewriting history.

### What LFS does

**Git LFS** (Large File Storage) is an add-on. Analogy: instead of
keeping a heavy statue in the filing cabinet, you keep a small card that
says "the statue is in the warehouse, shelf 42". LFS:

1. Stores a tiny **pointer file** (a few lines of text) in Git.
2. Stores the real big file on a separate LFS server (GitHub provides one).
3. Downloads the real file only when you check out that version.

How to read this: left is what lives inside your Git history, right is
what lives on the LFS server. The arrow is the link between them.

```
  GIT REPO (small, fast clone)            LFS SERVER (on GitHub)
  ----------------------------            ----------------------
  commit D*
   |- README.md   real text, stored normally
   |- design.psd  POINTER FILE (about 130 bytes):
        version https://git-lfs.github.com/spec/v1
        oid sha256:4d7a21...  ----------->  design.psd (500 MB, real bytes)
        size 524288000                      found by that oid (hash)

  git push : uploads the big file to the LFS server, pointer goes in Git
  git checkout/clone : Git reads the pointer, downloads the real file
```

What changed: the commit stores only the 3-line pointer, so the repo
stays small; the 500 MB file lives once on the LFS server per version.

Set it up once per repo:

```bash
git lfs install
```

Expected output:

```
Updated Git hooks.
Git LFS initialized.
```

(Notice: it installs hooks! Same mechanism you just learned.)

Tell LFS which files to manage:

```bash
git lfs track "*.psd"
```

Expected output:

```
Tracking "*.psd"
```

Meaning: any file ending in `.psd` is now handled by LFS. Use other
patterns for your case: `*.mp4`, `*.onnx`, `*.zip`. The quotes stop your
shell from expanding `*` before LFS sees it.

That command wrote a rule into `.gitattributes`, so commit that file too:

```bash
git add .gitattributes
git add design.psd
git commit -m "Add design file via LFS"
```

Check what LFS is handling:

```bash
git lfs ls-files
```

```
3f2a9c1b8e * design.psd
```

The `*` means the real content is stored locally; `-` would mean only the
pointer is present.

Doubt? "Why must I commit `.gitattributes`?" Because that file is how
your teammates' Git learns which files are LFS files. Without it, their
clone would treat the pointers as ordinary tiny text files.

Caution: track files BEFORE the first commit of them. Files already
committed in old history stay big unless you migrate them
(`git lfs migrate import`).

## `.gitattributes` — Line Endings and File Handling

### Why do we need this?

Here is a real, annoying problem. A **line ending** is the invisible
character(s) marking the end of a line of text.

- Windows uses two: `CRLF` (`\r\n`, "carriage return + line feed").
- Mac and Linux use one: `LF` (`\n`, "line feed").

Analogy: two people typing the same letter, one presses Enter once, the
other presses Enter twice. The words are identical, but a strict
character-by-character comparison says every line differs.

If a Windows teammate saves a file with CRLF while others use LF, then
`git diff` can show **every single line as changed**, though nothing
meaningful changed. The one real change is buried in noise.

What it looks like:

```bash
git diff --stat
```

```
 src/app.py | 240 +++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++
 1 file changed, 120 insertions(+), 120 deletions(-)
```

240 changed lines in a file where you edited one line. That is the symptom.

### First attempt: the personal setting `core.autocrlf`

```bash
git config --global core.autocrlf true     # Windows
git config --global core.autocrlf input    # Mac / Linux
```

Meaning:

- `true` (Windows): when you check out files, Git converts LF to CRLF so
  your Windows tools are happy; when you commit, it converts CRLF back to
  LF. The repository always stores LF.
- `input` (Mac/Linux): on commit, convert any CRLF to LF; on checkout,
  change nothing.

The weakness: this is a *personal* setting. It is not stored in the repo.
If even one teammate forgets to set it, they will commit CRLF files and
poison the history for everyone.

### Better: a committed `.gitattributes` file

Because it is a normal file inside the repo, it travels with every clone,
so the rules are defined once for everyone, regardless of personal config.

```gitattributes
# .gitattributes
* text=auto
*.sh text eol=lf
*.bat text eol=crlf
*.png binary
```

Line by line:

- `* text=auto` — for every file (`*`), let Git detect whether it is text,
  and if so normalize its line endings.
- `*.sh text eol=lf` — shell scripts are text and must always use LF,
  even when checked out on Windows (a CRLF would break them on Linux).
- `*.bat text eol=crlf` — Windows batch files must always use CRLF, even
  on Mac/Linux.
- `*.png binary` — this is not text. Never convert line endings or show
  text-style diffs. (Converting bytes inside a picture would corrupt it.)

Pattern on the left, attributes on the right. It is the same pattern
syntax as `.gitignore`.

Already have files with the wrong endings? After committing
`.gitattributes`, re-normalize:

```bash
git add --renormalize .
git status
```

Expected output:

```
Changes to be committed:
	modified:   src/app.py
	modified:   scripts/run.sh
```

Commit that once, in its own commit (for example "Normalize line
endings") so the noise is isolated and not mixed with real changes.

### Same file as LFS

You just saw this file in the LFS section: `git lfs track` writes a line
like `*.psd filter=lfs diff=lfs merge=lfs -text` into `.gitattributes`.
One file serves two roles: "how to normalize line endings" and "which
files LFS manages". Commit it early in any repo with contributors on more
than one OS.

### Check what applies to a file

```bash
git check-attr -a design.psd
```

```
design.psd: diff: lfs
design.psd: merge: lfs
design.psd: filter: lfs
design.psd: text: unset
```

Each line is an attribute Git applies to that file.

## Signed Commits — Verified Authorship

### Why do we need this?

Git does not check who you are. The name and email on a commit are just
text you configured. Anyone can type:

```bash
git config user.name "Linus Torvalds"
```

and commit as him. Analogy: anyone can write any return address on an
envelope.

A **signature** is a cryptographic proof attached to a commit. It says
"this commit was created by someone holding this private key". Analogy:
a wax seal that only you can press.

Quick vocabulary:

- **Private key** — a secret file on your computer. Never share it.
- **Public key** — its matching file you can share. Others use it to
  check your signature.
- Signing uses the private key. Verifying uses the public key.

### Setting up SSH signing

You already made an SSH key in Lesson 07 for GitHub login. The same key
can sign commits. (The older alternative is GPG, which is more complex.
SSH signing is simpler.)

```bash
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
```

What each line does:

- `gpg.format ssh` — use SSH keys for signing (the setting name says
  "gpg" for historical reasons).
- `user.signingkey ...pub` — which key to use. You point at the *public*
  file; Git finds the matching private key via your SSH agent.
- `commit.gpgsign true` — sign every commit automatically, so you cannot
  forget.

Make a commit:

```bash
git commit -m "Signed commit"
```

Expected output:

```
[main 7d3e1a9] Signed commit
 1 file changed, 1 insertion(+)
```

The output looks normal; the signature is stored invisibly. Check it:

```bash
git log --show-signature -1
```

Expected output (needs an allowed-signers file, see note below):

```
commit 7d3e1a9... (HEAD -> main)
Good "git" signature for you@example.com with ED25519 key SHA256:AbC...
Author: Your Name <you@example.com>

    Signed commit
```

`Good ... signature` means verification succeeded. If instead you see
`No signature`, signing was not applied. To make *local* verification
work, Git needs a list of trusted keys:

```bash
echo "you@example.com $(cat ~/.ssh/id_ed25519.pub)" > ~/.ssh/allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.ssh/allowed_signers
```

### Make GitHub show "Verified"

Doubt? "I signed, but GitHub shows no badge." Cause: GitHub has your key
registered only for login, not for signing. Fix: in GitHub go to
Settings -> SSH and GPG keys -> New SSH key, paste the same public key,
and choose the key type **Signing Key**. (You add the same key a second
time, with a different type.) Then new commits show a green **Verified**
badge.

Many companies turn on "Require signed commits" in branch protection for
`main` (Lesson 11), so unsigned commits are rejected.

## Commit Message Conventions at Scale: Conventional Commits

### Why do we need this?

A messy history looks like: "fix", "stuff", "more changes". A convention
makes each message carry a machine-readable label, so both humans and
tools can understand it at a glance.

**Conventional Commits** is a popular convention: start the message with
a type, a colon, then a short description.

```
feat: add search filter to results page
fix: guard against None response in fetch_status()
docs: update README setup instructions
refactor: extract retry logic into its own module
test: add coverage for empty-input edge case
chore: bump requests to 2.32
```

What the types mean:

| Type | Meaning |
|---|---|
| `feat` | a new feature for users |
| `fix` | a bug fix |
| `docs` | documentation only |
| `refactor` | code restructure, behavior unchanged |
| `test` | adding or fixing tests |
| `chore` | maintenance (dependency bumps, build config) |

Your filtered log becomes very readable:

```bash
git log --oneline
```

```
e5f6a7b test: add coverage for empty-input edge case
c4d5e6f fix: guard against None response in fetch_status()
a3b4c5d feat: add search filter to results page
```

Why tools love it: a tool like `semantic-release` reads these prefixes to
decide the next version number automatically. Version numbers look like
`MAJOR.MINOR.PATCH` (for example `2.4.1`):

- a `fix:` triggers a PATCH bump (2.4.1 -> 2.4.2),
- a `feat:` triggers a MINOR bump (2.4.1 -> 2.5.0),
- a breaking change (marked with `!`, like `feat!: drop Python 3.8`)
  triggers a MAJOR bump (2.4.1 -> 3.0.0).

Even if you use no tooling, it is worth adopting for readability.

Also from earlier lessons: write the description in the imperative mood
("add", not "added"), like a command. Think of finishing the sentence
"If applied, this commit will ...".

## Disaster Recovery Playbook — Staying Calm

### Why do we need this?

Nearly every Git disaster is recoverable, because Git almost never
deletes data right away (Lesson 03 and the reflog in Lesson 06). What
makes things permanent is panic: running several more commands trying to
fix it.

Analogy: when your test environment breaks, you read the logs first
rather than randomly re-running deploy scripts.

### The seven steps. Work through them in order, every time.

**1. Stop. Do not run more commands yet.** Take a breath. Each extra
command can bury the evidence of what happened.

**2. Run `git status`: where am I right now?**

```bash
git status
```

```
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)
```

It tells you the current branch and whether you are in the middle of
something (merge, rebase, cherry-pick). Notice it even suggests the
escape command.

**3. Run `git log --oneline --all --graph`: what does history look like?**
This shows all branches, not just the current one. Is the commit you
"lost" visible anywhere?

**4. Run `git reflog`: the undo history.** If a commit or branch seems to
have vanished, it is almost always here.

```bash
git reflog
```

```
7d3e1a9 HEAD@{0}: reset: moving to HEAD~2
a3b4c5d HEAD@{1}: commit: Add search filter
c4d5e6f HEAD@{2}: commit: Fix None guard
```

Reading it: `HEAD@{n}` means "where HEAD was n moves ago". Here a bad
`reset` moved HEAD back two commits, but `a3b4c5d` (your lost work) is
listed on line 2. Recover it:

```bash
git reset --hard a3b4c5d
```

That moves your branch back to the lost commit. (Or make a safe branch
pointing at it: `git branch rescue a3b4c5d`.)

**5. Stuck mid-operation? Abort.** Use the one matching the operation:

```bash
git merge --abort
git rebase --abort
git cherry-pick --abort
```

Each returns you to exactly where you were before that operation began,
safely. No output means success; run `git status` to confirm you are back.

**6. Before any `--hard` reset or `--force` push, ask one question:**
"Could this erase something that someone else needs, or something that
reflog cannot bring back?" (Reflog only covers commits you had locally.
Uncommitted edits destroyed by `reset --hard` are gone, and so is anything
overwritten on the remote by a force push.) If you are unsure, create a
safety branch first; it costs nothing:

```bash
git branch backup-before-i-mess-this-up
```

It creates a label on your current commit. Whatever happens next, you can
return to it.

**7. When truly stuck: the nuclear option.** Clone a fresh copy of the
remote into a new folder and copy your uncommitted work over manually.

```bash
cd ..
git clone git@github.com:you/repo.git repo-fresh
```

It costs a few minutes and guarantees a clean slate. This is a perfectly
valid professional move, not a failure.

### Decision tree: what went wrong, which command?

How to read this: start at the top question, follow the labelled branch
(yes / no or the symptom) down to the command in the last column.

```
  Something went wrong. (Stop. Run: git status)
        |
        v
  Is an operation half-done? (merge / rebase / cherry-pick in status)
        |
   yes -+---> git merge --abort | git rebase --abort
        |     | git cherry-pick --abort
        |
   no   v
  Did a commit or branch seem to VANISH?
        |
   yes -+---> git reflog, then
        |     git reset --hard <hash>  or  git branch rescue <hash>
        |
   no   v
  Is the bad commit already PUSHED / shared?
        |
   yes -+---> git revert <hash>   (adds a new undo commit)
        |
   no   v
  Bad commit is local only
        +---> git reset --soft HEAD~1   (keep changes)
              or git commit --amend     (fix the last commit)
        |
        v
  Secret committed?  ---> revoke it first, then git filter-repo
  Totally stuck?     ---> fresh git clone, copy your work over
```

What changed: nothing in your repo; this is a map. Note the order:
abort first, reflog second, revert for shared history, reset only for
private history.

### Common confusion: which "undo" do I use?

| Situation | Use |
|---|---|
| Mistake on private, unpushed commits | `git reset` (or amend) |
| Mistake already pushed/shared | `git revert` (adds a new commit that undoes it; rewrites nothing) |
| Lost a commit | `git reflog` |
| Operation went wrong midway | `git <operation> --abort` |

## Branching Strategies — Three Team Workflows

### Why do we need this?

Git lets you make branches freely, but it does not tell a team how to use
them. A **branching strategy** is the team's agreement on: which branches
exist, who may merge into which, and how code reaches production. Three
common agreements are below, from simplest to most ceremony.

Analogy: Git is the road; a branching strategy is the traffic rules.

### 1. GitHub Flow (simplest; used by most web teams)

Rules: `main` is always deployable. Every change gets a short-lived
feature branch, a pull request (PR), review, then merge.

How to read this: time runs left to right. Each row is one branch. A
`/` leaves `main` (branch created), a `\` returns to `main` (merged).

```
            E---F           feature/login
           /     \
  A---B---C-------G---H     main
                  ^
          merge commit (parents: C and F)
```

What changed: `feature/login` left `main` at C, got two commits (E, F),
and came back as merge commit G. Then `main` moved on to H.

### 2. Trunk-Based Development (fastest; needs strong CI and tests)

Rules: everyone merges into `main` (the "trunk") at least daily. Branches
live hours, not days. Unfinished work is hidden behind a feature flag (an
`if` in the code that keeps it switched off).

How to read this: same drawing style, but notice how tiny the side rows
are. Many small merges instead of one big one.

```
            E       G         1-commit branches, merged within hours
           / \     / \
  A---B---C---M---F---N       main
```

What changed: two one-commit branches (E and G) each left and rejoined
`main` quickly (merge commits M and N). F was committed straight to
`main`. `main` never drifts far from any branch.

### 3. Git Flow (most ceremony; used for versioned releases)

Rules: `main` holds only released versions. `develop` is where finished
features collect. `release` branches polish a version. `hotfix` branches
fix urgent bugs in production.

How to read this: five rows, top to bottom: hotfix, main, release,
develop, feature. Lines between rows show where a branch starts or merges.

```
                                H    hotfix
                               / \
  A---------------------------M---N    main
   \                         /
    \                   R---S    release
     \                 /     \
      B---C-------D---E-------F---G    develop
           \     /
            X---Y    feature
```

What changed, in time order (left to right):
- `develop` is created from `main` (the long `\` down from A).
- `feature` (X, Y) leaves `develop` at C and merges back as D.
- `release` starts from `develop` at E, gets a fix (S), then merges into
  BOTH `main` (M = version released) and `develop` (F).
- `hotfix` (H) leaves `main` at M, merges back as N; G is the same fix
  also merged into `develop` (link not drawn, to keep the picture clean).

| Strategy | Branch lifetime | Good for |
|---|---|---|
| GitHub Flow | days | web apps, continuous deployment |
| Trunk-based | hours | mature CI, feature flags |
| Git Flow | weeks | shipped versions (mobile, firmware, installers) |

## The Top-1% Checklist

Read each item as a habit, with its reason.

- [ ] Commits are small, focused, and have imperative-mood messages
      (small commits are easy to review, revert, and bisect)
- [ ] `.gitignore` is set up before the first commit, not after a secret
      leaks (cleaning history is painful; prevention is free)
- [ ] Feature branches, never direct commits to `main` (`main` stays
      always working)
- [ ] PRs are small enough to review in one sitting (big PRs get
      rubber-stamped)
- [ ] `git status` before anything destructive (know your state first)
- [ ] Rebase only unpushed/personal history; revert (never reset) for
      shared history mistakes (never change history others have copied)
- [ ] `--force-with-lease`, never bare `--force` (it refuses to overwrite
      commits on the remote you have not seen)
- [ ] Branch protection + CI required checks on every shared repo
      (machines enforce the rules, not memory)
- [ ] Know `reflog` exists and trust it instead of panicking
- [ ] Comfortable enough with the object model (Lesson 03) that no Git
      command feels like unexplainable magic anymore

## Recap in 5 Lines

1. `.gitignore` hides untracked junk and secrets; already-tracked files
   need `git rm --cached`; a leaked secret must be revoked first, then
   scrubbed with `git filter-repo`.
2. Set `git config` once (identity, editor, aliases); local overrides
   global.
3. Hooks run your checks automatically but are not shared via Git, so
   teams use the `pre-commit` framework; LFS and `.gitattributes`
   handle big files and line endings.
4. Signed commits prove authorship, and Conventional Commits make history
   readable by people and tools.
5. In a disaster: stop, `git status`, `git reflog`, abort or back up
   before anything destructive, and re-clone if needed.
